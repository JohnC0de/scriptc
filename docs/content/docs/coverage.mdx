title: "Coverage Reports"

`scriptc coverage` analyzes a program without building an executable. It reports how many executable statements compile to native code and groups unsupported operations by diagnostic code. Counts describe the program being analyzed, not JavaScript or Node.js support in general.

<span id="static-programs" />

## A native program

```console
$ cat hello.ts
const who: string = process.argv.length > 2 ? process.argv[2] : "world";
console.log(`hello, ${who}`);

$ scriptc coverage hello.ts

  statements analyzed   2
  compile statically    2  (100%)

  fully static — all analyzed statements compile to native code.
```

## Reading the report

<table>
  <thead><tr><th>Field</th><th>Meaning</th></tr></thead>
  <tbody>
    <tr><td><code>statements analyzed</code></td><td>Executable statements in application code, excluding dependency implementation code.</td></tr>
    <tr><td><code>compile statically</code></td><td>Statements that compile to native instructions.</td></tr>
    <tr><td><code>blockers</code></td><td>Unsupported operations with counts, reasons, and diagnostic codes.</td></tr>
    <tr><td><code>npm package compilation</code></td><td>Native package compilation outcomes and refusal reasons.</td></tr>
  </tbody>
</table>

Unreached code and deferred JavaScript operations are reported separately. A deferred operation can remain in a compiled package, but executing it raises a runtime error. A successful build therefore does not establish compatibility for every package API.

## Diagnostic codes

Coverage uses the same diagnostic codes as `scriptc build`. Common examples include:

- `SC2020`: a declared standard-library or Node.js API has no supported compiler implementation.
- `SC2012`: this API form cannot compile natively.
- `SC2013`: a package cannot compile natively; inspect the package-specific reason and the [dependency guide](/docs/dependencies).
- `SC1100`: a value crosses an unsupported checked-value boundary. Narrow or cast the value as directed by the diagnostic.

## Type errors

Coverage requires a program that typechecks. If type checking fails, the report identifies the errors instead of producing statement counts. Fix those errors before interpreting compilation coverage.

## External host type declarations

An embedder may provide modules that are absent from `node_modules`. Use `--external-types` to map an exact bare module specifier to the embedder's declaration file during analysis. For example: `scriptc coverage src/core.ts --external-types @native-sdk/core=types/native-sdk-core.d.ts`.

The option is repeatable. Relative declaration paths resolve from the current working directory. Supported declaration extensions are `.d.ts`, `.d.mts`, and `.d.cts`. Relative declaration imports and re-exports are included, so the mapped file can be an `index.d.ts` barrel. Project-owned code using these types participates in coverage; type-only imports add no runtime boundary.

The mapping supplies types for analysis, not a runtime implementation. Value imports and uses remain `SC1010` external-host blockers while analysis counts the rest of the application. This option is available only for coverage; builds require a module implementation or runtime integration.
